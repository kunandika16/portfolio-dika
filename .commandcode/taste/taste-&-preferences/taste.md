# Taste & Preferences
- Prefers to communicate in Bahasa Indonesia (Indonesian), and wants project content/copy written in Indonesian rather than English. Confidence: 0.9
- Wants the assistant to scan and study the existing project structure/codebase before starting implementation work (explore-first workflow). Confidence: 0.8
- Prefers clarifying scope with questions before large content work rather than guessing details (e.g., asked which projects, what format, what language — and answered). Confidence: 0.6
- Does not want build/verification commands run after every change; only run builds (e.g., `npx craco build`) when the user explicitly asks. Confidence: 0.9
- Prefers data-driven architecture: content/case-study data kept in a dedicated data file (e.g., `src/data/caseStudies.js`) keyed by id, with pages made dynamic from route params rather than static/dummy content per page. Confidence: 0.7
- When changing a project's metadata or assets (e.g., company name, cover image), expects the change applied consistently everywhere it appears (data file AND any page that displays it — e.g., homepage and work list), not just one spot. Confidence: 0.9
- For modals/overlays/lightboxes, prefers them rendered via `createPortal` to `document.body` so they are not clipped by parent containers with `filter`/`overflow-hidden` — plain `position: fixed` inside such containers is unacceptable. Confidence: 0.6
- On case-study article pages, image galleries should be shown as thumbnail cards placed at the very bottom (after the Result section), opening a detail/lightbox view only when clicked — not large inline images. Confidence: 0.75
- For project case studies, expects the full set of available screenshots (all images in the project's image folder) to be used as a gallery, with a designated image as the main content screenshot — while the header/cover image stays unchanged; when designating a gallery, the user explicitly excludes the images already used as cover/content ("gambar di folder ... sebagai gallery selain uangku-mobile, uangku dan login"); images are organized in per-project folders (e.g., `public/images/projects/<project>/`) with `*-cover.png` (card/hero) and `*-isi.png` (main content) naming, and the user points to the folder when designating roles. The user also incrementally adds newly available screenshots to the gallery as they become ready. Confidence: 0.85
- Distinguishes image roles by filename semantics: the `*-isi.png` (content) image is meant to appear inside the case-study article body (rendered inline in the article content), NOT in the work-page slider/card — the slider keeps only the cover image (`travel.png`), and content screenshots must not be added there. When an asset is placed in the wrong spot, the user corrects its placement precisely ("itu letaknya di isi articlenya"). Confidence: 0.8
- Prefers a consistent 16:9 image ratio (`aspect-video` + `object-cover`) across all image display surfaces — article/header hero images (fitting 1920×1080 at all breakpoints), hero slider cards, and Work page project covers — so everything is uniform and nothing is awkwardly cropped ("supaya seragam dan tidak terpotong"), rather than fixed heights or responsive multi-ratio sizing. Confidence: 0.85
- Wants tech stack items in the portfolio displayed with accompanying brand logos/icons alongside the text (not just plain-text chips) — e.g., every stack shown with its official logo. Confidence: 0.7
- Wants UI design that avoids "AI slop" template patterns (generic ambient gradient orbs, multi-color gradients, shimmer/glow animations, decorative icons, random stock photos, duplicate decorative stats); prefers professional, clean, elegant design grounded in real project content with a restrained single-accent palette; stock photos are replaced with real local assets (e.g., the About profile portrait was changed from Unsplash to `/images/profil/dika2.png`). Confidence: 0.85
- Likes subtle background textures for elegance — thin patterns (fine grid, dot matrix, faint diagonal lines) with a soft radial mask that fades at the edges, layered behind content so it doesn't distract or hurt readability; wants the treatment applied to EVERY section/page of the site (hero, projects, stats, about, work, article, footer), not just one spot. Confidence: 0.85
- Pattern intensity must be very faint — rejects patterns that are "terlalu kasar dan rame" (too coarse/busy); prefers generous spacing (grid ~48px) with very low opacity (≈0.03–0.05, dots ≈0.10–0.12) so textures read as a whisper of depth, not visible lines. Confidence: 0.8
- Wants the frontend-design skill to be used (activated) when enhancing UI/design work. Confidence: 0.7
- Prefers the portfolio to have a focused, single-discipline positioning (e.g., software developer only) — copywriting in hero/about and category tabs should all be consistently aligned to that focus, with unrelated creative categories (graphic design, video editing) removed entirely rather than kept. Confidence: 0.8
- Prefers empty tabs/sections to show an honest "coming soon" state rather than being filled with repurposed or placeholder content. Confidence: 0.6
- User's system drive (C:) has very limited free disk space — a global tool install (`uv tool install`) failed with "not enough space on the disk"; account for disk constraints when installing tooling, check available space first, and the user will proactively ask about disk/resource requirements before proceeding. Confidence: 0.8
- Prefers global developer tools/CLIs to be installed on a non-system drive (e.g., `D:\App-Data\...`) — redirecting cache, tool, bin, and python dirs there so C: is not touched — rather than installing on the system drive by default. Confidence: 0.8
- Cares about token/cost efficiency in the AI-assisted workflow: interested in tools and approaches that reduce token usage across sessions (e.g., a persistent codebase knowledge graph built once via AST so repeated questions don't require re-reading source files), and asks follow-up questions about a tool's token-saving benefits before adopting it; has actually adopted such tooling (the project contains a `graphify-out/graph.json` knowledge-graph output used as a data source). Confidence: 0.6
- Cares about dark mode quality across the whole app: every text/background must stay contrasting in dark theme (proper `dark:` variants — e.g., `dark:text-white`/`dark:text-slate-400`, dark card backgrounds/borders) with complete coverage of all components/sections; partial fixes that leave some text unreadable are unacceptable. Confidence: 0.8
- Cares about dark mode across the whole app: text must stay readable/contrasting against dark backgrounds, and every component/page needs proper `dark:` variants (e.g., `dark:text-white`/`dark:text-slate-400`, dark card backgrounds/borders) — partial fixes covering only some sections are not acceptable; performs visual QA on the rendered UI across themes and reports contrast issues. Confidence: 0.8
- Background texture/pattern treatments must NOT make sections transparent: a CSS `mask-image` radial fade applied to an element that carries its own background color fades the whole element (including the `bg-*` color), making it see-through so elements behind it (e.g., a dark fixed footer) show through. Fade masks are only safe on pure transparent pattern overlay divs (Hero, Footer); sections/pages with their own background must keep their background solid (pattern without the fade mask). Confidence: 0.8
- Reviews the rendered UI visually (sends screenshots of the running app) and reports visual/rendering defects (e.g., "background looks transparent"); expects visual QA findings to be diagnosed and fixed across all affected elements, not just one spot. Confidence: 0.6
- Delegates case-study narrative writing to the assistant: provides only factual project parameters (image, modules, role, tech stack) and expects the assistant to develop the full case study details (overview, challenges, solution, features, result) autonomously rather than asking back — "detail case study-nya kamu kembangkan sendiri". Confidence: 0.7
- Treats user-provided project facts (actual role, modules, tech stack, exact project/company naming) as authoritative for portfolio entries: invented/placeholder data (e.g., a placeholder `company: "Client"` or a wrong project name like "IdeTravel.com") gets corrected to what the user names, and new items must also be added where they are rendered so the provided facts show up everywhere. Confidence: 0.8
- User actively edits files directly in the IDE outside the AI session (e.g., manually rewrote the `screenshots` array in `caseStudies.js` between turns; again triggered "file berubah di luar sesi" during the WebP conversion), so the file state can diverge from what the assistant last wrote; the assistant should re-read the current file before continuing rather than assuming its prior edits are intact, and should flag such divergences to the user. Confidence: 0.7
- Prefers the same project screenshot to serve as both the case-study header/hero image and the project card cover image. Confidence: 0.45
- Wants the hero slider to showcase real project cover images (local assets under `public/images/projects/...` or `public/images/cover/...`) instead of generic Unsplash stock photos; when the user adds a new cover image for a project, it should also be added to the hero slider so the hero stays in sync with project covers ("tambahkan juga gambar covernya di hero section"). Confidence: 0.9
